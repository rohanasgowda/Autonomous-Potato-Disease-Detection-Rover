# Troubleshooting

## Common failure points

Phase 6 stores intermediate state so failures can be diagnosed via the SQLite session row.

### Grid Movement failures

- If a custom `GridMovementController` is provided, verify that `move_to_grid_position()` and `stop()` do not raise exceptions.
- If movement integration is not yet implemented, Phase 6 runs with `NoOpGridMovementController`, and no actual rover movement occurs.

### Camera capture failures

- `CameraCapture.capture()` first attempts Picamera2 and then falls back to OpenCV.
- If `source_image` is supplied, Phase 6 copies the image into the capture directory instead of using the camera.
- Check that `PHASE6_CAPTURE_DIR` is writable.
- Use `--source-image` to isolate camera hardware issues.

### Classification and inference failures

- Phase 6 passes the captured image to `phase4.app.inference.run_tflite_prediction()`.
- Confirm the model and labels files exist at `PHASE6_MODEL_PATH` and `PHASE6_LABELS_PATH`.
- If the Phase 4 model or config is invalid, the workflow fails in the inference stage and records the failure.

### Treatment generation failures

- Treatment recommendations are generated by `OpenRouterClient.generate_treatment()`.
- If the treatment agent fails, Phase 6 records the `treatment_failed` stage and returns a failed workflow result.

### Backend sync failures

- `BackendClient.upload_detection()`, `upload_recommendation()`, and `check_inventory()` are executed only when backend configuration is present.
- Failed backend sync is captured in the session error JSON and does not remove earlier successful scan data.
- Synchronization may be skipped with `--skip-backend`.

### Telegram notification failures

- Telegram delivery is attempted if `--skip-telegram` is not set.
- Errors from Telegram are recorded in the session row under `telegram_json` and error JSON.
- A failed Telegram delivery may result in a final sync status of `telegram_failed`.

## Inspecting session records

The local session database is stored at `PHASE6_LOCAL_DB_PATH` or default `logs/phase6_sessions.db`.

The `phase6_sessions` table includes:

- `session_id`
- `created_at`
- `updated_at`
- `image_path`
- `detection_json`
- `treatment_json`
- `backend_json`
- `inventory_json`
- `telegram_json`
- `error_json`
- `sync_status`

### Recovery behavior

- `create_session()` inserts or replaces a session row and sets `sync_status` to `captured`.
- `update_session()` updates completed stages and preserves earlier stage data.
- If an error occurs in capture, inference, or treatment, the workflow returns a `WorkflowResult` with the error stage and the session remains available for inspection.

## Integration test behavior

Phase 6 includes end-to-end workflow tests in `phase6/tests/test_phase6_workflow_e2e.py`.

- Tests mock `generate_session_id()` and `run_tflite_prediction()`.
- `build_detection_payload()` is mocked to avoid dependency on external image payload details.
- Fake backend and Telegram clients verify backend sync and notification behavior.
- A grid movement test confirms `move_to_grid_position()` and `stop()` are invoked before capture.

## Debugging tips

- If imports fail, ensure the workspace root is on `PYTHONPATH` so `phase3`, `phase4`, and `phase6` import correctly.
- Use `--source-image` to rule out camera problems.
- Check `sync_status` and `error_json` in the SQLite session row for the exact failure stage.
- Verify `PHASE6_CAPTURE_DIR` and `PHASE6_LOCAL_DB_PATH` directories exist and are writable.
